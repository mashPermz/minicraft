# v3開発フローの振り返り(2026-07-04)

体制: 非同期Sonnet5サブエージェント2体(worktree分離)が製造、親セッション(Fable 5)が指示・統合・レビュー・ブラウザ検証・PR作成。成果は PR #3(スカイライト・水流・モブ・効果音+レビュー修正1件)。

## うまくいったこと(継続推奨)

- **変更禁止ファイルの明示による担当分割**: Agent B に world.rs/mesher.rs/storage.rs/blocks.rs を「読み取り専用」と指示した結果、統合時の競合は意味的競合1件(mobs.rs テストの Chunk 初期化子)のみ。ファイル所有権ベースの分割は Rust の並行開発と相性が良い。
- **品質ゲートと最終レポート様式のプロンプト内定義**: cargo test / clippy×2ターゲット / wasmビルドを両エージェントに義務付けたことで、統合前の品質が揃い、レポートの粒度も比較可能だった。
- **PROGRESS.md「ハマりポイント」の指示書への組み込み**: flood_add の set-at-enqueue 等、過去の地雷の再踏襲を防げた。ナレッジをリポジトリに蓄積→次のエージェントのプロンプトに注入、というループは機能している。
- **ストール時に親が worktree を直接調査してから再開指示**: 盲目的な再開ではなく、親がテストを実際に走らせて「ハングは既に存在しない・失敗は1本だけ」と状況を確定させてから SendMessage したことで、1往復で復帰できた。

## 改善点

### 1. サブエージェントの環境前提を最初から渡す(ストールの根本原因)
Agent A の2回のストールは「macOS に `timeout` コマンドがない」ことに起因する迷走だった(存在しないコマンドでラッパーを組もうとして SIGALRM ハック等に脱線)。さらに悪いことに、最初の私の再開指示自体が `timeout` を提案していた。
**対策**: エージェント向けプロンプトの定型「環境ノート」を作る(OS、coreutils 有無、テストスイートの正常所要時間、`~/.cargo/registry` での API 確認方法など)。「フルスイートは正常なら数秒で終わる」という基準値があれば、ハング判断も早い。今回の教訓は PROGRESS.md に記載済みだが、リポジトリ非依存の内容は別の場所(親のメモリ or テンプレ)に持つべき。

### 2. worktree の分岐元をエージェント任せにしない
修正エージェント(v3.1)の worktree は main から切られており、修正対象コード(feature/v3 の成果)が存在しない状態で開始した。エージェントが自力で feature/v3 を ff-merge して回復したが、これは運が良かった(判断を誤れば main 基準のパッチが返ってきた)。
**対策**: worktree 分離エージェントの起動前に、親が「分岐元ブランチ」を確認・指示に明記する。もしくは起動直後の必須手順として「`git merge --ff-only <base>` で対象ブランチを取り込め」を定型化する。

### 3. 親レビューの「軽微」判定の扱い
モブ攻撃の block_t 近似は、統合時の親レビューで Suggestions #3 として検出していたが「実害は稀、v4送り」と自己判断した。その後ユーザーレビューで同じ点が指摘され、結局 v3 内で修正した。検出はできていたのに、送り/即修正の判断を親が独断した点が反省。
**対策**: レビューで見つけた「今回は直さない」項目は、PR 本文か PROGRESS.md の既知課題に必ず載せて、送り判断をユーザーが覆せる形にする(今回は会話内のレビュー結果にしか残していなかった)。

### 4. ブラウザ検証の再現性
合成入力イベント(`movementX/Y` 付き mousemove、KeyboardEvent、mousedown 長押し)でヘッドレスのままプレイ操縦(移動・視点・採掘・松明設置・飛行)まで検証できたのは収穫。ただし手順がこの会話にしか残っておらず、スクリーンショットも `evidence_of_tests/` に保存できていない(preview ツールは画像をファイル出力できない)。
**対策**: 操縦スクリプトを `scripts/` か専用スキルとして永続化し、headless Chrome CLI ベースでスクリーンショットをファイル保存できる形にする。v4 以降の回帰検証(洞窟の暗さ・水流の見た目)がワンコマンドになる。

### 5. ビルドキャッシュの重複
worktree ごとに target/ がフルビルドになる(1エージェントあたり数分)。今回の規模では許容範囲だが、エージェント数を増やすなら `CARGO_TARGET_DIR` の共有 or sccache の検討余地あり(並行 cargo のロック競合には注意)。

## そもそもの疑問(ユーザーに確認したいこと)

1. **実プレイFBのループ**: 「実プレイ再確認待ち」項目が v1.1 から積み残しになっている(岸ジャンプ・BGM・三人称・v2洞窟探検・今回の効果音バランス等)。ヘッドレスでは音量バランスと操作感は検証できないため、どこかで人間の実プレイ→FB反映のイテレーションを挟みたい。v4 着手前に一度プレイテスト回を設けるのはどうか。
2. **バージョンスコープの決め方**: v3 は PROGRESS.md の候補リストから親が独断で4機能を選んだ。結果的に異論はなかったようだが、「遊び手として欲しい順」があるなら候補に優先度を付けてもらえると、スコープ選定の精度が上がる。
3. **suggestion_box の運用**: このディレクトリの想定読者と運用(セッションごとに1ファイル? 返信や解決済みマークの形式?)を教えてほしい。次回から所定の形式に合わせる。
4. **README「制作」節の表現**: 「Fable 5 の遺作」という記述があるが、これは意図した表現か。モデルは現役なので、事実性の観点で気になった(触らずに残している)。
